# Anargon's Tablet Tools - the firmware builder and digital twin (design)

<img src="../misc/AIdisclosure-most_docs.png" align="right" width="280" alt="Note: This document is mostly AI generated, with only minor corrections done by a human (stated to the AI).">

The tablet tool turns stock firmware into a modified image, checks it in a digital twin and can drive xppen-tools for an update. The chip core lives in the sibling `../gd32emu/` component; `EMULATOR.md` describes the shared interfaces. See `FIRMWARE_DESIGN.md` for tablet behavior and [verification](verification.md) for evidence and remaining hardware checks.

## Build overview

The builder reads a complete stock dump, resolves the firmware layout, applies guarded patches and writes an Intel HEX image. The digital twin runs that image through gd32emu's instruction and peripheral model. Only an image that passes those checks can proceed to xppen-tools for the confirmed tablet update.

gd32emu's chip core is compiled into the tool; xppen-tools remains a separate executable. The tablet's controller is a GD32F350C8T6 with 64 KB flash and 8 KB SRAM.

## Guiding rules

- **Never patch blind.** Every firmware location is found by its code (a signature), never assumed at a fixed address, and every change is guarded by a check that the firmware has the expected stock code at that spot. A location that cannot be found or code that does not match stops the interactive build with a specific diagnosis.
- **Never flash unchecked.** Every build is booted and exercised in the emulator first; a build that fails is never offered for flashing.
- **Bootloader writes are explicit.** Default builds leave the bootloader area alone. Enabling Bootloader Changes permits the firmware counter; the experimental Bootloader Counter also changes start-up code. Return-to-stock is a separate maintenance operation. A normal xppen-tools update replaces only the application area.

The shared core uses a deliberately small C# 5 subset: no generics, LINQ, `out`/`ref`, or unsigned types; strings are compared with `P.Eq` and bytes masked `& 0xFF`. Native platform bindings in `P` are outside that subset. Windows' .NET Framework 4 `csc.exe` builds the Windows application; the SDK project targets .NET 10 for self-contained platform packages.

## How a build is made (`BuildOne`)

1. Resolve the preset timing and settings; compute per-step readings and, if needed, trim them to fit the frame.
2. Validate the timing (frame budget, sample/pulse/tick limits) and any measured calibration profile. An actual build refuses invalid timing even when internal force state is set; compatibility probes collect code-site results.
3. Resolve the firmware layout of the input (`Fw.Use`; cached) and create an `Image` (a full 0x08003800-0x0800FFFF buffer pre-filled with 0xFF, the stock app copied in; added code starts at the firmware end).
4. Apply the patches in order. Each is a tagged, transactional group (`Image.Begin` / `Image.Fail`, see `Compat`): hardware divide, movement smoothing, interpolation, scan timing, AGC fix, 1 ms USB interval, max-pressure, band-edge, frame scheduler (`Sched.Patch`), calibration-pass LED hooks if requested, the locked version string, then the USB flash-count readout. A group that needs a missing firmware location is rolled back completely. After the tool's own groups come the modifications a patcher package added (`Build.AddPatch`, interface `IPatch`), each in its own `Package: <name>` group and named in the options text as `PACKAGE=<name>`, then the package's options that are on (`Build.AddSetting`), each in a `Package option: <name>` group and named as `PACKAGE-OPTION=<KEY>`; the calibration measurement, ALPI training and return-to-stock builds leave them out. An option a package hides (`Build.HideSetting`) is unavailable on every preset, so every build treats it as off; `Build.Option` changes a copy of the settings list, and `Build.ClearPatches` puts the built-in list back. The undo record is written after them, so it covers package changes too.
5. Write the Intel HEX (and optional `.bin`), and log every byte change.

`Build.ReadInput` and `Twin.LoadImage` share `IntelHex` in `atf_hex.cs`: record sizes, digits, checksum, record type, end marker and flash bounds are checked. Conflicting overlaps are refused; identical overlaps and correctly sized entry-address metadata are accepted. The scatter-load table still determines whether the application is complete.

### Signature-based firmware layout (`Layout`, `Fw`)

Patch code names every firmware location by its address in the reference build (2025-02-14): `Fw.A(0x08009A1C)` is "the flash-erase routine, wherever this firmware has it"; `Fw.Ptr(0x0800766C)` is the word stored at a location (a pointer to a table). `Layout.For` resolves all of them for one firmware image:

- each location has a **signature** in `atf_symbols.cs`: a window of reference bytes around it with every build-dependent byte masked (BL/B.W encodings, LDR/ADR literal offsets, words pointing into flash, bytes this tool rewrites, bytes that differ between the verified builds). Since R42 the file stores no firmware bytes: only the window's mask (`x` must match, `.` masked), a 16-bit quick check of its first four fixed bytes, and the first 64 bits of the SHA-256 of the window with masked bytes set to 0. A position matches when both agree (`Layout.Quick16`, `Layout.WindowFp`, `Sha256`);
- it is searched in the firmware region (halfword steps). **Exactly one** match resolves it; none or several leave it unresolved and `Fw.A` throws a "firmware location not found" `Stop`. `Image.Fail` rolls the group back: probes mark it incompatible, normal builds refuse it, and the retained internal force flag can only omit that group;
- for a **verified build** (`Layout.KNOWN`: build string, end, CRC; February and December) every resolved address is compared with the stored one; a difference marks the location unresolved (the image is not the untouched build its string names);
- `Layout.FindEnd` reads the firmware end from the start-up code's scatter-load table (the zero-init entry's load address);
- the twin resolves its hooks from the image it runs (`Twin.LayoutOf`), so the masked rewritten bytes matter: a built image still resolves.

Adding or changing a firmware address: write `Fw.A(0x...)` with the February address, then rerun the generator. Its inputs are the stock dumps and a log of every byte the tool can write (the regression matrix output): `python -I tools/mksig.py atf_symbols.cs WRITES.txt FEB.bin DEC.bin:080041CC-080042A7=-2,080042A8-08005867=-4,0800589C-0800FFFF=12 -- atf_*.cs`. The map after the December dump is only the ground truth the generator checks its signatures against. It picks the shortest window (at least 12 fixed bytes, inside the symbol's function when possible) that matches once in every build at the right place, and fails loudly for a location it cannot sign. An address used without a signature is an internal error at build time. When adding one location by hand, generate into a separate file and copy only the new line into `atf_symbols.cs`, so every existing line stays byte-identical (they were made from the full write log). A patcher package hands its own lines to `Layout.AddSignatures` at run time: identical duplicates are ignored, a line that differs from a known one stops with an error, and the layout is resolved again. The generator expands wildcards itself, so `-- atf_*.cs` also works from cmd and PowerShell.

### The assembler (`Asm`) and `Image`

`Asm` is a hand-written Thumb-2 assembler. Branch offsets are even byte displacements from PC+4: Cbz/Cbnz accept 0..126, Bcc -256..254 and short B -2048..2046. PushW/PopW cover 32-bit register lists with lr, and Mov32 builds a constant with movw/movt. Added code is placed in the free flash after the stock image ("the cave"). `Image` holds the bytes and the patch log, allocates the cave, and guards every in-place edit with `Expect(addr, stockBytes)`.

### `Expect` has three modes

(A BL/B.W at a site is compared by its destination - the resolved February target - not by its bytes, since its encoding depends on where it sits.)

- **Normal**: if the firmware's bytes at a patch site are not the stock code, it throws - the build is refused rather than patch the wrong offset (which is how `.data` gets corrupted).
- **Probe** (`Image.probe`): it records the per-modification `tag` into `probeAll`/`probeBad` instead of throwing, so a whole build's sites can be checked in one pass without writing anything. This drives `Compat`.
- **Internal force flag** (`Image.force`): retained low-level behavior can log a byte mismatch and apply that edit. The CLI does not expose this flag or offer a confirmation that bypasses incompatibility checks. Missing addresses are never guessed, and timing/profile validation still applies to actual builds.

### Compatibility check (`Compat`)

`Compat.Check` runs a full `BuildOne` in probe mode and returns which modifications' code sites do not match the loaded firmware, or need a firmware location (site, called function, table, literal) that the layout could not find, out of how many were checked. The CLI builds normally if all sites are compatible; any incompatibility stops the build and lists affected modifications. Internal probe/force mechanisms are not an interactive bypass. Timing constraints always apply to an actual build. `AnargonsTabletTools --compat IMAGE [--rate PRESET]` prints the report directly. The February reference fixture passes the compatibility check. Other registered layouts still require their full fixture-backed run for the release being verified.

## The digital-twin gate (`Cli.Gate`)

Every build is loaded into the twin and checked in parallel at full PC speed: boot reaches the main loop, USB enumerates with the right VID/PID/interfaces/bInterval, the AGC leaves at least one summed sample, and a weak pen is detected at four frequencies. A build with Multi-coil Read also runs its routine against its C# copy on every position call of a pen swept across the coils (at touch and 5 mm); one difference fails the build. Measurements then run against the simulated 72 MHz clock: frame period/work, processing time, cursor latency (vs stock firmware), and still-pen spread. Missing required measurements fail the gate. These are model estimates; physical flash timing and analog behavior are not calibrated by these checks. A build that fails is never offered for flashing.

Each `Machine` copies the input flash before running, so firmware writes in one parallel check cannot affect another. `Twin.PositionReport` accepts coordinates only from in-range ID 7 reports or framed calibration position page E1 with its saved in-range flag. Signal, frequency and counter pages do not count as position measurements.

## Pen and receiver models (twin side, in `atf_twin.cs`)

- `fade` (default): the ADC reads the ring-down envelope.
- `integrate` (`--receiver integrate`): the ADC reads the integral of the ring-down since PB8 went low; shorter readings detect proportionally less. This board-model inference helps compare builds; its signal scale and noise are not calibrated against a physical tablet.

## Hover stages (R45-rc3)

Stages: 0 fast, 1 Steady Hover, 2 reach (VB+0). At 800/1000 Hz a found pen is acquired into Steady Hover and steps
straight to the fast stage when its level reads strong (`Sched`, label `m_nc`).
- **Step-up level per stage (`Build.StepUpLevel`, `cfg.enterUp1` / `enterUp2`):** the fast stage's boost-enter level
  as the slower stage reads it, `enter x ringup(stage pulses) / ringup(fast pulses) x 1.25`, with
  `ringup(n) = 1 - exp(-n pi / 300)`. Before rc3 a slower stage was compared with `enter` itself, so a pen too weak
  for the fast stage read strong there and flapped (tablet: 24 fast + 3 Steady Hover frames, about 37 times a
  second), and reach stepped up at about 16 mm in the twin, where the fast stage lost the pen.
- **Reach hold (`Build.REACH_HOLD` = 0.6):** the reach stage's scan and sweep drop levels are 0.6 of `Drop()`; its
  pick-up levels stay. Twin hover hold at ULTRA 22.0 -> about 26 mm, no pick-ups without a pen.
- **Tilt Frame Skip (setting `tiltskip`, `cfg.tiltSkip`):** in the plan step, a tilt frame (type 1, 2, 4 or 8) is
  planned as a normal frame (V+2 = 0: no tilt line, no tilt scan) while VB+0 is 0 (fast stage) and the report's
  pressure is under 4 (hovering). Tilt keeps its last value there. Touching, Steady Hover and reach measure tilt as before.
- **R45-rc4 ladder (`Build.BuildLadder`, `Cfg.lad`, `Sched.LadderTable`):** steps every `LAD_PERIOD_STEP` (25 us)
  of frame time, each read at least `LAD_STEP` (1.2) x the last, kept down to the level where its noise reaches
  `NoiseRef` (ULTRA's fast stage at 1.12 x its drop level); the firmware's `m_air` steps down after 8 / 2 frames and
  up after 4 at the measured ratio x 1.25 (`VL`). A found pen starts at `Cfg.ladAcq` (40 pulses).
- **R45-rc4 Switch Match (setting `smatch`, `cfg.switchMatch`):** `start_x` copies C[6], C[7], C[3] and VBX+8 (or
  VB+0) to SW+4..7; `swm`, called in the restart before Jump Rejection, corrects D+8 / D+10 after a change; the search
  routine resets it. Tick table per step from the frame periods. C# copy: `SwitchMatch.Model`. rc4 (2): default on
  again; a coil-window switch needs 15 mm/s (`10 x 4 |Bn| >= 3 Bd`) and 16 frames without a switch of that axis,
  drive-step and ladder-step switches (r5 bit 2) only the 16 frames.
- **R45-rc4 (2) Window Scale (setting `wscale`, `cfg.winScale`; ULTRA only, not with Multi-coil Read):** the two
  position calls (X 0x080083BE, Y 0x0800840A) go to `ws_x` / `ws_y`, which copy the three stack arguments, call the
  stock routine 0x08005432 and, while VB+0 = 0, add `(r - centre x 1018) x k >> 12`, k from 9 Q12 knots per axis
  over PRESSURE+6 (table in flash, `WindowScale.Table`). C# copy `WindowScale.Apply`; the twin's position-call check
  (`McTwinBoard.ws`) compares every call with it.
- **Coil Gains (PR1; setting `cgain`, `cfg.coilGains`; in Misc. Optimizations; ULTRA, needs Window Scale, not
  with Multi-coil Read or in the lab build):** `CoilGains.EmitScale` inside `ws_x` / `ws_y`, after the three stack
  copies and before the stock call, while VB+0 = 0, the centre coil (`[sp+36]`) is 0..N and reads = S+5 - AGC delay
  > 0: each line `((line - (FLOOR_A x reads + FLOOR_B)) x G_k) >> 8`, G_k from a 2 x 40 halfword table (coil k at
  slot k + 2; Q12; `CoilGains.Table`), at `CoilGains.STRENGTH` = 589 per mille of the measured difference. C# copy
  `CoilGains.Scale`; the twin's position-call check (`McTwinBoard.cg`, found by `CoilGains.Installed`) compares the
  stock routine's arguments with it. CLI `--no-coil-gains`.
- **R45-rc5 Dynamic Anti-Chatter (setting `dac`, `cfg.antiChatter`; paced presets; default on):** `dachat`, called
  with Bl after ALPI on the final position. Per axis d2 = p0 - 2 p1 + p2 from the two previous inputs (RAM DAC);
  over the threshold (0.10 mm, halved in report mode 2) out = p0 + ws (p1 - p0), ws = w x min(|d2| - thr, thr) / thr
  (hardware divide), w per Steady Hover step or hover stage from a flash table (0.4 ms / frame period, at most 0.5).
  History cleared on pen loss and in the search restart. C# copy `DynamicAntiChatter.Model`; at most 133 cycles.
- **R45-rc5 Coil Linearization (setting `clin`, `cfg.coilLin`; paced presets; default on):** `clin`, called with Bl right
  before `apfilt` (ALPI), on D+8 (X) and D+10 (Y). Per axis the phase inside the coil from the R43 grid (X coil k at
  163.53 - 5.080 k mm, Y 96.42 - 5.083 k mm), then position + T(phase), T linear between 64 knots (flash table, 65
  bytes per axis, 1/200 mm + 128, `CoilLinearization.Table`); in report mode 2 the units are doubled for the phase
  and the correction halved. Nothing kept between frames; about 60 cycles per axis. The table is table B
  (`CoilLinearization.TX` / `TY`); the first table (`AX` / `AY`) is only the Filter Arranger's CL-A.
- **Misc. Optimizations (setting `misc`, R45):** one switch for `smatch`, `wscale`, `clin` and `dac`
  (`Build.MISC_KEYS`, `Build.SetMisc`); the screens show only it (`Cli.ShowGroup`), the four keys and their flags stay
  for the command line. `--no-misc-optimizations` turns all four off; the file name then says `noMO` only.
- **Bootloader Timer Off (setting `systick`, `cfg.systickOff`):** the R45-rc2 `SYST_CSR` clear in the search-restart
  routine, now a setting (default on).

+0 three 16-byte stage entries (period, scan pulses/tick/samples, sweep pulses/tick/samples, 4 thresholds), +48 quick search, +64 long search, +80 build id, +96 tilt frame types.

## Multi-coil Read (R43)

Setting `multicoil`, experimental, off by default, FAST, RAPID and ULTRA (Anargon: not worth it below 500 reports per second). The two calls of the stock position routine (`0x08005432`, from X `0x080083BE` and Y `0x0800840A`) go to `MultiCoil.Emit`'s routine instead. It replaces the stock arithmetic where its fit applies, and hands the call to the stock routine (with the caller's registers, stack and return address) where it does not:

- **Inputs:** the stock routine's own arguments (the five line sums around the peak line, the centre coil), plus the peak line index and the reads per line (samples minus that axis's AGC delay).
- **Gates (stock routine instead):** the peak is not on the centre line, a neighbour line is above the centre line or both equal it, the reads are not positive, or the centre line is less than 8 above the floor (or absurdly large).
- **Floor:** `69 x reads - 60` is subtracted (R43: 216 / 288 / 632 at 4 / 5 / 10 reads). Each line is limited to 0..centre line and scaled so the centre line is 2048..4095. Lines of coils that do not exist (past an edge) are left out.
- **Start:** the 3-line parabola, rounded to a 1/16-pitch grid point.
- **Fit:** two Gauss-Newton steps to the measured response, equal line weights, the pen signal eliminated each step, at most 0.3 pitch per step. Each step reads one table word per line (`MultiCoil.Table`: 91 words, response and its change at 1/16-pitch grid points, Q12), so there is no interpolation and no divide per line; three divides per step. If the first step cannot be solved the parabola is used, if the second cannot the first step's result.
- **Effective range:** fixed at 17/16 of the measured one. A per-axis tracked range (the first R43 version) was no better on the recordings and needed RAM and time.
- **RAM:** none.
- **Cost:** measured alone (single-stepped, no interrupts, 6000 inputs): the fit path at most 282 cycles, the stock routine 503 mean / 544 most; where the stock routine runs, the gates add at most 31 cycles per axis. So a frame takes less time with it than without. Charged `MC_US = 1`; the core suite checks the measurement against it.
- **Specification:** `Claude-workarea/experiments/mcint.py` (the same integer arithmetic). The core suite checks the C# copy (`MultiCoil.Calc`) against it on 64 line copies recorded on Anargon's tablet, every gate, and the edges; and the firmware against the C# copy in the twin, on every position call, at FAST, RAPID and ULTRA.
- **Twin pen:** the twin's pen uses the same measured response, stretched to an effective range (1.34 pitches at touch, wider with height). Its line sums have no floor, unlike the tablet's.

## Tablet calibration (two-pass)

Pass 1 builds telemetry firmware whose pen reports carry the firmware's own readings; the app (`CalSource`: `HidSource` on real hardware, `TwinSource` in the twin) walks three pen positions (R45-rc2: light touch, normal hover, highest hover; with ALPI there are no guided steps: the training measures the same values in the background, `Cli.FromTraining`), then pass 2 builds the tuned firmware. Report mode 4 bypassed both telemetry send hooks. A calibration build now pins the existing report-mode RAM byte to mode 2 before report construction; normal builds keep vendor routing. The reader requires ID 7 plus calibration markers and a recent in-range position/pressure page. Preflight verifies actual signal and position telemetry before timed holds. Stock frequency is the default; experimental startup frequency tuning and Dual-coil Mode are excluded from measured threshold profiles. Only fast-stage pick/drop and the jump margin are tuned, with thresholds capped at preset defaults. No-pen receiver noise and boost/second-coil behavior are not measured. Calibration files record format/profile and are fully validated before options change.

`Cli.Calibrate` gates and flashes pass 1 after the run's backup (`Cli.BeforeFlash`: one complete backup per run, the startup capture included; a running startup capture is waited for), verifies telemetry, then collects the five holds. Measurement builds disable bootloader writes; the final normal build retains the user's bootloader settings. `HidSource` closes in `finally` on success, failure or cancelled input. Command-line `--calibrate` then builds, gates, backs up and flashes the normal firmware; failed measurement can restore the normal preset with defaults. The wizard keeps its explicit final flash choice. `calibrationFirmwareActive` tracks a possibly installed measurement image from the first update attempt until a normal update succeeds. An update can write firmware before reporting a verification or reconnect failure, so a failed measurement update keeps that state set. Exiting with it set reports failure and explains how to restore normal cursor reports.

## Flashing, the flash counter, and the per-user PC store

**Flash-count readout (rev 35, `Patches.CounterString`):** the stock GET_DESCRIPTOR handler's fall-through stall (`Fw.A(0x0800AF72)`) is redirected to a routine that answers only STRING index 173 with `ADTC1:<B|F|N>:<6 digits>`, built on request at RAM `0x20001F80` from the counter page `0x08002C00`, and jumps to the handler's own send path (`Fw.A(0x0800B04E)`); every other request still stalls. The twin's USB check reads string 173 and the build check shows it. **R44:** the calibration-pass build also answers strings 176-179 (`Sched.ZONE_STRING` + 2 x target + recording; target 0 none, 1 the drawing area's centre): they set the LED zone at RAM `0x20000F54` (state, LED, state ^ 0xA5) and answer `ADTZ1:<target><recording>`. Every other build stalls them as before. The stall path leaves r0 / r1, the stall's arguments, untouched. `Cli.LiveCount` reads it on the PC (`P.HidIndexedString`), `Cli.DumpCount` from the dumps, `Store` last. The page, record layout and USB readout are deployed compatibility contracts; preserve them.

**Repair tool (rev 35, `atf_repair.cs`):** `Repair.Analyse` checks a full `main.bin` against a verified build: code pages by CRC (`StockRef.PAGE_CRC`) and the end from `0x0800C188` by CRC (`StockRef.END_CRC`; up to R42 Part 3 the stock bytes themselves, `StockRef.TAIL`). An erased or changed end is restored from the user's own copy: `Repair.FindEnd` searches `Repair.SearchRoots` (the dump's folder and its parent, the output folder, the current folder, the program's folder and its parent; 3 levels deep, nearest first) for a 64 KB dump, application `.bin` or Intel HEX whose end matches `END_CRC` once this tool's known edits are undone. With none, the result is `needCopy` and the tool asks for one. Damaged code needs a verified stock copy of that build; the reconstructed application must match the build's full CRC. An erased settings page at `0x08003400` is normal after an update and is not by itself firmware damage. Its final settings word (+0x18) determines whether settings are present. Since R42 `Repair.Examine` (also used by the flasher's input and backup checks) first undoes changes at this tool's own patch sites (`Repair.EDIT_AT` / `EDIT_STOCK`, per build): a code page counts as edited, not damaged, only if it then matches its stored CRC, and the reconstructed firmware is used only when its whole CRC-32 matches. Damage means an erased end (16 or more bytes 0xFF where stock is not). After every backup, `BackupCapture.CheckRestoreImages` renames an xppen-tools `ic902-code.bin` / `ic902-stock.hex` that stops before the firmware end to `*.INCOMPLETE-DO-NOT-FLASH`; a file that cannot be renamed is reported ("do not flash it") and the backup still counts (R43 review). Since the R43 review `Build.ReadInput` refuses a verified build with any code page changed in an unknown way (`pagesOther`), with or without known edits; pages past the end of a truncated input are counted apart (`pagesMissing`) and not compared. `Layout.For` keeps the last resolved layout and reuses it only for the same bytes (it compares a copy, not only the CRC-32).

`Repair.Patcher` redirects the firmware's start (`Fw.A(0x0800395C)`) to a stub after its end. If that final settings word is erased, the stub uses the firmware's erase/program helpers to restore settings, writes boot state 1 last, then follows its DFU-entry software reset (`Fw.A(0x0800B070)`). `Repair.FixWorks` inspects the machine's resulting flash: settings must be restored and the tablet must either wait in update mode or resume firmware reports after the update window. Runtime faults fail verification. The stock image and patcher also pass the normal gate on the restored settings image. `Repair.LooksDamaged` rejects damaged build inputs and diagnoses captured backups.

Flashing is driven through xppen-tools, which asks for its own typed confirmation. Every new capture preserves a complete 64 KB image in `dumps/<timestamp>/` and atomically publishes the latest successful capture in `last-dump/ic902-main.bin`. Interactive startup begins that capture in the background and returns the tablet from DFU; input selection waits for it. Every actual flash still takes a fresh complete backup and verifies its firmware. External command success requires exit status zero; a dry run has a separate command-preview path. Failed captures preserve the previous valid dump and cannot authorize flashing.

`StartupBackup.Begin` stores captures under the executable folder; `StartupBackup.Wait` runs before source selection and again on program exit. Quiet background helpers receive closed stdin and log output rather than consuming menu input. `Cli.BeforeFlash` stores another capture under the selected output folder, checks the connected firmware against the source build, then leaves the tablet in DFU for the update. Each folder has its own `last-dump/` and `dumps/` subdirectories. `FlashSteps` resolves and quotes absolute paths, requires a successful process status without a reported verification error, and increments the local count only on success. Closed prompt input does not acknowledge a warning or authorize another step. `--flash-dry-run` runs no tablet commands and cannot be combined with live calibration/recovery or the wizard.

The readout prefers live USB string 173, current calibration telemetry, then captured dump/history counts. Its labels are `[According to Bootloader]`, `[According to Firmware]` or `[According to local PC]`. A live `N` response means no device counter and suppresses stale dump counts. The per-user `Store` contains a separate local count of successful updates made by this tool profile, plus warning acknowledgements. It does not identify individual tablets or automatically cache observed tablet counts: `Store.NoteFlashCount` is retained but has no current caller. The maximum over available dump/history counts is chosen by `Cli.DumpCount`, not by syncing them into the local counter. State defaults to `%APPDATA%\AnargonsTabletTools\state.ini`, or `~/.local/state/AnargonsTabletTools`; `ADT_STATE_DIR` overrides it and the legacy `ATF_STATE_DIR` is still read.

## Bootloader counter + reset-vector self-heal (tool side)

The implementation is in `atf_sched.cs`. This optional, experimental feature hooks the bootloader's `set_boot_state` so the bootloader counts every firmware erase. It is installed once by the firmware on the first boot after flashing, with a stored stock copy of the boot page and the hook word committed last. When enabled it also redirects the reset boot-jump to a repair stub kept in a never-erased bootloader page, so an interrupted install self-heals on the next boot. One irreducible window remains (the single reset-vector page rewrite); it is opt-in only and never part of a normal build.

`Sched.blclean` refuses an unknown reset redirect and verifies the complete restored reset page before erasing the stub or counter pages. `Cli.ReturnToStock` gates the cleanup image, takes a fresh backup, flashes it and shows the uninterrupted-power wait. Before the final stock flash it gates the stock application and captures the tablet again. `Cli.StockBootloaderRestored` requires boot code 0x08000000..0x080027FF to match the stock source and both extension pages 0x08002800..0x08002FFF to be erased. Vendor settings/data at 0x08003000..0x080037FF may differ. Failed verification keeps the cleanup application and its restoration data in place.
